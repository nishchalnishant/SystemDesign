# Idempotency keys

**Claim in one sentence.** A lost *response* is indistinguishable from a lost *request* to the client, so any retry of a non-idempotent write can duplicate the effect — and the fix is a client-supplied key the server uses to deduplicate.

## Why it happens

The client sends `POST /payments`. The server charges the card. The response is lost to a network blip. The client sees a timeout — which it cannot distinguish from "the server never got it" — and retries. The user is charged twice.

No amount of server-side care fixes this, because the ambiguity lives in the client's view of the world. The client has to supply something that lets the server recognize the second request as the same request.

## The mechanism

```
POST /v1/payments
Idempotency-Key: 7c9e6679-…

→ server stores key → result, TTL ~24h
→ retry with the same key returns the original response, does not re-charge
```

The key is generated by the client, once, *before* the first attempt — and reused across all retries of that logical operation. A key generated per HTTP attempt is useless.

Which endpoints need it: anything non-GET that moves money, sends a message, or creates a resource. `PUT` and `DELETE` are naturally idempotent by HTTP semantics; `POST` is not, which is why this is fundamentally a POST problem.

## What you say in an interview

> "Any non-GET that moves money or creates a resource takes an `Idempotency-Key` header. The client generates it once before the first attempt and reuses it on every retry — the server stores key-to-response with about a 24-hour TTL and replays the stored response instead of re-executing. The failure it prevents is a lost response, where the client can't tell whether the charge happened."

## The concurrent-retry subtlety

Two retries can arrive while the first is still in flight. Storing the key *after* completion leaves a window where both execute. The key insert has to happen atomically at the start:

```sql
INSERT INTO idempotency_keys (key, status) VALUES (?, 'IN_PROGRESS');
-- unique constraint violation ⇒ someone else owns it
```

The loser then either waits and returns the stored result, or returns `409 Conflict`. Making the key row and the business write part of the same transaction is what makes this actually correct.

## Probes you should survive

- *"Why not have the server dedupe on request content?"* → Two legitimately identical payments (same amount, same merchant, minutes apart) are a real thing. Content hashing rejects valid requests.
- *"What if the same key arrives with a different body?"* → `422`. It signals a client bug — reusing a key for a different operation — and silently returning the old response would hide it.
- *"Why a TTL rather than keeping keys forever?"* → Unbounded growth. 24 hours comfortably exceeds any sane client retry window.
- *"Two retries at once?"* → The key insert must be atomic and up-front, or both execute. Unique constraint on insert, not a check-then-write.
- *"Isn't `PUT` already idempotent?"* → At the HTTP level yes, which is why this is a POST problem. But a `PUT` with side effects — sending an email — needs a key too.
